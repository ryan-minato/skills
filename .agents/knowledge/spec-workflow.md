# Specification Workflow

Read this before starting a change that alters what a skill or a
repository tool does, before creating issues from a change, before editing
anything under `openspec/`, and before marking a pull request ready.

Level: **spec-anchored**. `openspec/specs/` is the living description of
current behavior, and every behavior change updates it through an
archived change. Selected because this library is maintained indefinitely
and installed by others, so the agreement about what a skill does must
outlive the session that wrote it.

Tool: **OpenSpec**, pinned to the version in the `openspec_version`
variable of the `justfile` (verified 2026-09-03 against `openspec --help`
and the tool's documentation). Before running or documenting any OpenSpec
command, run `openspec --help`; commands and skill names have changed
between releases and are not recorded here.

## Artifacts

| Path | Holds | Edited by |
|---|---|---|
| `openspec/config.yaml` | Schema selection and short pointers to this repository's conventions. Never restates them. | maintainer |
| `openspec/specs/<domain>/spec.md` | The current behavior of one domain, as requirements with scenarios. **Source of truth for behavior.** | the archive step only, never by hand |
| `openspec/changes/<slug>/` | One change in flight: `proposal.md`, `design.md`, `tasks.md`, and delta specs under `specs/<domain>/spec.md`. `<slug>` equals the branch slug. | the change's author, through the OpenSpec skills |
| `openspec/changes/archive/<date>-<slug>/` | Completed changes. | the archive step only |
| `.agents/skills/openspec-*/` | Skills generated by the CLI. | `just spec-sync` only; never by hand |
| `ARCHITECTURE.md`, catalog `README.md` files | As-built description of everything no spec covers. Descriptive, not normative. | humans and agents, as the repository changes |

## Domains

- One domain per public skill, named after the skill:
  `openspec/specs/<skill-name>/spec.md`. Its requirements describe what an
  agent that loaded the skill observably does; its scenarios are the
  skill's behavioral test cases.
- One domain per repository tool: `skill-validation`
  (`scripts/validate_skills.py`, `scripts/check_skill.py`), `marketplace`
  (`scripts/gen_marketplace.py`), `harness-checks`
  (`scripts/validate_harness.py`, `scripts/check_pr_policy.py`,
  `scripts/sync_issue_metadata.py`).
- A domain exists only once a change touches it. Never backfill specs for
  skills or tools nobody is changing; the as-built files above cover them.

## Source of truth

| Fact | Rules | Points to it |
|---|---|---|
| What the repository is for | `README.md` | this file, `openspec/config.yaml` |
| Skill quality and conventions | `.agents/knowledge/skill-quality.md`, `AGENTS.md` | `openspec/config.yaml`, specs never restate them |
| Behavior of a skill or tool | `openspec/specs/<domain>/spec.md` | issues, pull requests, behavioral tests |
| Acceptance of a change | the scenarios in `openspec/changes/<slug>/specs/` | the Task issue form's Specification field, the pull request's `Spec:` line |
| Repository mechanics | `ARCHITECTURE.md` and the knowledge files | specs never restate them |

A file listed under "Points to it" may summarize in one line and must
link; it never restates the fact.

## Lifecycle

1. **Proposed** — the change directory exists with a proposal and delta
   specs (the propose skill; `plan-clarification` runs the clarify step
   until no assumption is silent).
2. **Approved** — the maintainer approves the proposal and delta specs, in
   the issue or on the draft pull request. An agent never approves a
   change it wrote.
3. **Implemented** — every task is done and every scenario passed: for a
   skill, the behavioral tests in the `skill-authoring` project skill,
   derived from the scenarios; for a tool, the commands the scenarios name.
4. **Archived** — inside the same pull request, before it is marked
   ready: the archive skill merges the delta into `openspec/specs/` and
   moves the change under `changes/archive/`. `main` therefore never holds
   an unarchived change.

Deviation found during implementation: stop, revise the change (the
update skill), get the revision approved, then continue.

## Specifications and tracked work

- The change owns what is built, why, and the acceptance scenarios.
- An issue owns who, when, and status. The Task form's Specification field
  names `openspec/changes/<slug>`; its acceptance field holds either
  executable criteria or a link to the change's scenarios, never both.
- A pull request names its change on a `Spec:` line and ticks "change
  archived" in its checklist. `Spec: none — <reason>` is allowed only for
  changes that alter no behavior (documentation, harness sync, tooling
  pins).
- Bug reports carry no spec: the expected behavior is the current spec,
  and the fix's change carries the delta.

## Verification in checks

`just spec-validate` runs the OpenSpec validator in strict mode over every
spec and change; `just check` includes it, and the `checks / spec` job
runs it in CI. The same job regenerates the OpenSpec skills and fails if
the committed copies differ from what the pinned CLI produces.

## Update this file when

- `openspec_version` in the `justfile` changes: run `just spec-sync`,
  re-verify the artifact table against `openspec --help`, and update the
  verification date above.
- The level or the approval owner changes.
- A domain naming rule changes.
- A second source of truth for any fact in the table appears — merge it
  back, do not let it stand.
