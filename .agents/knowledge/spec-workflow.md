# Specification Workflow

Read this before starting any tracked change — to a skill or to the
repository itself — before creating issues from a change, before editing
anything under `openspec/`, and before marking a pull request ready.

Level: **spec-anchored**. `openspec/specs/` is the living description of
current behavior, and every behavior change updates it through an
archived change. Selected because this library is maintained indefinitely
and installed by others, so the agreement about what a skill does must
outlive the session that wrote it.

Tool: **OpenSpec**, pinned to the version in the `openspec_version`
variable of the `justfile` (verified 2026-09-17 against `openspec --help`
and the tool's documentation). Before running or documenting any OpenSpec
command, run `openspec --help`; commands and skill names have changed
between releases and are not recorded here. Framework skill:
`openspec-workflow` (`skills/sdd/openspec-workflow`), which owns the
request automation below and its script.

## Artifacts

| Path | Holds | Edited by |
|---|---|---|
| `openspec/config.yaml` | Selects the `skill-change` schema and carries the apply and archive guidance the CLI injects. Never restates conventions. | maintainer |
| `openspec/schemas/skill-change/` | The project schema: artifact set, per-artifact instructions, and templates shaped for skill changes and repository changes (proposal, delta specs with `Trigger:` / `Behavior:` / `Handoff:` / `Script:` requirements, design with a verification plan, tasks). | maintainer, through a change |
| `openspec/specs/<catalog>/<skill-name>/spec.md` | The current behavior of one public skill, as requirements with scenarios. **Source of truth for behavior.** | the archive step only, never by hand — with one exception: a change that removes or reshapes a domain's capabilities corrects that domain's `## Purpose` line by hand in the same pull request and names the edit in its proposal |
| `openspec/changes/<slug>/` | One change in flight: `proposal.md`, delta specs under `specs/<catalog>/<skill-name>/` (none for a repository change), `design.md` (the approach's bounds — placement, description, dependencies, decisions with rejected alternatives, risks — and the verification plan written before implementation; part of the approval package, never a step list, never a secret or private datum), `tasks.md` (written after the closing). `<slug>` equals the branch slug. | the change's author, through the OpenSpec skills |
| `openspec/changes/archive/<date>-<slug>/` | Completed changes. | the archive step only |
| `.agents/skills/openspec-*/` | Skills generated by the CLI. | `just spec-sync` only; never by hand |
| `ARCHITECTURE.md`, catalog `README.md` files | As-built description of everything no spec covers. Descriptive, not normative. | humans and agents, as the repository changes |

## Domains

- One domain per public skill, at the skill's catalog path:
  `openspec/specs/<catalog>/<skill-name>/spec.md` (for example
  `openspec/specs/sdd/spec-driven-development/spec.md`). Its
  requirements describe what an agent that loaded the skill observably
  does; its scenarios are the skill's behavioral test cases. A skill that
  moves catalogs moves its domain in the same change.
- The repository itself — its environment, harness, tooling, checks,
  workflows, and documents — has no spec domain. A change to it is a
  **repository change**: an OpenSpec change whose `.openspec.yaml` sets
  `skip_specs: true`, with a proposal, a design (placement and verification
  plan), and tasks but no delta spec. The as-built files above describe it.
- A domain exists only once a change touches it. Never backfill specs for
  skills nobody is changing.

## Source of truth

| Fact | Rules | Points to it |
|---|---|---|
| What the repository is for | `README.md` | this file, `openspec/config.yaml` |
| Skill quality and conventions | `.agents/knowledge/skill-quality.md`, `AGENTS.md` | `openspec/config.yaml`, specs never restate them |
| Behavior of a public skill | `openspec/specs/<catalog>/<skill-name>/spec.md` | issues, pull requests, behavioral tests |
| Acceptance of a change | for a skill change, the scenarios in `openspec/changes/<slug>/specs/`; for a repository change, the verification plan in its `design.md` | the Task issue form's Specification field and the pull request's `Spec:` line, each a link to the change directory on its branch |
| Repository mechanics | `ARCHITECTURE.md` and the knowledge files | specs never restate them |

A file listed under "Points to it" may summarize in one line and must
link; it never restates the fact.

## Lifecycle

1. **Proposed** — the change directory exists with its approval package:
   the proposal, the delta specs (the propose skill; `plan-clarification`
   runs the clarify step until no assumption is silent), and `design.md`
   whenever the schema requires one (every change that touches a skill's
   description, adds or moves a reference, asset, or script, changes a
   dependency or handoff, touches a mirrored file, or is a repository
   change; optional only for a wording change inside one existing
   section). The draft pull request opens once that package is complete,
   with the package as its first content and `Phase: specification` in
   its body — never before the design, never after the task list.
2. **Approved** — the agent stops at the draft. The maintainer discusses
   the package on the pull request — the proposal, the delta specs, and
   the design's bounds (placement, decisions, rejected alternatives,
   risks, verification plan) — directs record changes in conversation
   (each pushed through the publish gate), and declares the discussion
   closed in conversation. The agent then reads the pull request's
   comments and review threads with their resolution state, lists every
   unresolved thread, every requested adjustment the package does not
   carry, and every contradiction, asks the maintainer to confirm the open
   items, and proceeds only when nothing is open or the open items are
   confirmed; the closing is noted on the draft's `Approval:` line. The
   review examines the outcome description — goals and scope,
   terminology, behavior, invariants, constraints, states, interface and
   data contracts, edge cases, security, acceptance — and the design's
   bounds; never `tasks.md`, which the author writes after the closing. A
   design that reads as an implementation procedure is rewritten as
   bounds before the draft opens. A pull request review approval is not
   the record: later pushes dismiss it. An agent never closes the
   discussion on a change it wrote.
3. **Implemented** — the task list written after the closing, every task
   done, and every scenario passed: for a skill, the behavioral tests in
   the `skill-authoring` project skill, derived from the scenarios and
   planned in the change's `design.md`. The body's phase becomes
   `implementation` once the record is archived; ready follows.
4. **Archived** — inside the pull request before it is marked ready, by
   the executor below; `main` never holds an unarchived change, and the
   `checks / spec` job fails a ready pull request that still carries one.

Deviation found during implementation: stop, revise the change (the
update skill), have the maintainer discuss and close the revision on the
draft, then continue.

## Pull request shape

Combined: one pull request carries the whole lifecycle. Selected because
this repository ships skills feature by feature and no consumer depends on
a stable contract (installed copies are never updated in place, so a
change reaches nobody until they reinstall). The pull request opens as a
draft when the approval package is committed, the approval gate is
exercised on that draft by closing its discussion, the task list follows
the reconciled closing, and marking it ready requests implementation
review. A change that also needs harness work
carries a companion repository change `<slug>-harness` on the same
branch. The default specification author is the implementing agent; the
maintainer approves.

## Archive executor

Every change is archived inside its own pull request before the pull
request is marked ready, so `main` never holds an unarchived change; the
archived record is frozen under review, and a defect found in it goes to
the pull request's Validation section or a follow-up change, never into
the archive. The executor is either:

- **By hand** — every task ticked (never before its verification ran),
  then the archive skill (a skill change's delta lands in
  `openspec/specs/`; a repository change's record only moves under
  `openspec/changes/archive/`), `just spec-validate`, and a commit
  `docs: archive the <slug> change` on the branch.
- **The `spec/archive` label** — applying it (an authorized remote write)
  makes the `spec / archive` workflow archive every related change whose
  tasks are all ticked, commit as the Actions bot, push to the branch,
  recompute the status labels, remove the label, and post a summary; it
  refuses everything when any related change has an open task. Its push
  leaves the pull request's checks in an approval-required state until the
  maintainer clicks **Approve workflows to run**. A pull request from a
  fork gets the local commands in a comment instead and archives by hand.

Selected because the repository runs Actions and a bot that pushes to the
pull request's own branch needs no ruleset bypass. Archiving after the
merge by a job pushing to `main` was tried and dropped: a user-owned
repository cannot grant the Actions app a bypass.

## Request automation

`openspec-workflow`'s automation, mirrored into `.github/workflows/` and
`scripts/spec_changes.py`: a pull request's *related changes* are the
change directories its diff touches (an archived directory counts under
its change name). `checks / spec` runs the strict validator and fails a
ready pull request holding an unarchived related change (a warning while
it is a draft); on a push to `main` any change outside `archive/` fails.
`/spec show [<slug>] [proposal|design|tasks|specs|all]` and
`/spec status [<slug>]` posted as pull request comments by a collaborator
or the author get a reply from `spec / command`. `spec / labels` keeps
`spec/archived` | `spec/unarchived` and `spec/not-started` |
`spec/in-progress` | `spec/done` on every pull request from its related
changes' task lists; read them, never set them by hand. Locally,
`just spec-check` reproduces the check and `just spec-changes <command>`
the rest.

## Specifications and tracked work

- The change owns what is built, why, and the acceptance scenarios.
- An issue owns who, when, and status. The Task form's Specification field
  names `openspec/changes/<slug>`; its acceptance field holds either
  executable criteria or a link to the change's scenarios, never both.
- A pull request names its change in its Specification section: a
  `Spec:` line linking the change directory on its branch —
  `[openspec/changes/<slug>](https://github.com/ryan-minato/skills/tree/<branch>/openspec/changes/<slug>)`
  — so a reviewer reaches the record in one click, a `Phase:` line
  (`specification` until the discussion is closed, `implementation` once
  the record is archived), one link per file of the approval package with
  `tasks.md` marked as written after the closing, and the approval state;
  it ticks the two specification items in its checklist. The body opens with the goal and
  states the value under `Why`; Changes (permalinks to the commits) and
  Validation (scenario results) are filled only when the pull request is
  marked ready, so the approval surface carries no implementation. An
  issue's Specification field holds the same link. Tracker objects
  navigate to the record; they never copy it. A repository change is named the same way; its archive moves
  the record without touching `openspec/specs/`. A skill change that also
  needs harness work carries a companion repository change named
  `<slug>-harness` on the same branch, and the pull request names both on
  their own `Spec:` lines.
- An issue opens when the requirement appears, with the raw requirement,
  owner, and priority and no acceptance criteria; it links the change
  record once that record exists. Discussion of a specification in an
  issue thread is deliberation; the record is the file on the branch when
  the maintainer closes the discussion.
  `Spec: none — <reason>` is allowed only for a change too small to plan
  (a pin bump, a typo).
- Bug reports carry no spec: the expected behavior is the current spec,
  and the fix's change carries the delta.

## Verification in checks

`just spec-validate` runs the OpenSpec validator in strict mode over every
spec and change; `just check` includes it. The `checks / spec` job runs
`just spec-check` (the validator plus the unarchived-change rule) on pull
requests and `just spec-changes check --all` on `main`, then regenerates
the OpenSpec skills and fails if the committed copies differ from what the
pinned CLI produces.

## Update this file when

- `openspec_version` in the `justfile` changes: run `just spec-sync`,
  re-verify the artifact table against `openspec --help`, and update the
  verification date above.
- The level, the approval owner or mode, the rule for when a design is
  required, the change request shape, or the archive executor changes; a
  workflow, command, or label of the request automation is added, renamed,
  or removed.
- A domain naming rule or the catalog layout changes.
- The project schema gains, loses, or reshapes an artifact: update the
  artifact table, `skill-authoring`, and the pull request template together.
- A second source of truth for any fact in the table appears — merge it
  back, do not let it stand.
