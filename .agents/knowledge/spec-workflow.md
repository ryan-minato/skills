# Specification Workflow

Read this before starting any tracked change — to a skill or to the
repository itself — before creating issues from a change, before editing
anything under `openspec/`, and before marking a pull request ready.

Level: **spec-anchored**. `openspec/specs/` is the living description of
current behavior, and every behavior change updates it through an
archived change, because this library is maintained indefinitely and
installed by others: the agreement about what a skill does must outlive
the session that wrote it.

Tool: **OpenSpec**, pinned by `openspec_version` in the `justfile` and run
through Deno (`just install-tools`). Before running or documenting an
OpenSpec command, run `openspec --help`; commands and skill names change
between releases and are not recorded here. Framework skill:
`openspec-workflow` (`skills/sdd/openspec-workflow`), which supplied the
request automation below; this repository's `scripts/spec_changes.ts` is
its own port and binds nothing in the skill.

## Artifacts

| Path | Holds | Edited by |
|---|---|---|
| `openspec/config.yaml` | Selects the `skill-change` schema; the apply and archive guidance the CLI injects, as pointers | maintainer |
| `openspec/schemas/skill-change/` | The project schema: artifact set, per-artifact instructions, templates | maintainer, through a change |
| `openspec/specs/<catalog>/<skill-name>/spec.md` | Current behavior of one public skill. **Source of truth for behavior.** | the archive only (one exception below) |
| `openspec/changes/<slug>/` | One change in flight: `proposal.md`, delta specs, `design.md`, `tasks.md`; `<slug>` equals the branch slug | the change's author |
| `openspec/changes/archive/<date>-<slug>/` | Completed changes | the archive only |
| `.agents/skills/openspec-*/` | Skills generated by the pinned CLI | `just spec-sync` only |
| `ARCHITECTURE.md`, catalog `README.md` files | As-built description of everything no spec covers; descriptive, not normative | anyone, as the repository changes |

The exception: a change that removes or reshapes a domain's capabilities
corrects that domain's `## Purpose` line by hand in the same pull request
and names the edit in its proposal.

The generated `openspec-*` skills change only through `just spec-sync`
after `openspec_version` is bumped; `checks / spec` fails when the
committed copies differ from the pinned CLI's output. They describe the
tool's generic flow; where they disagree with this file, this file wins.
In particular `openspec-archive-change` is not this repository's archive
executor (`## Archive executor and the freeze`).

### Artifact roles

Each artifact of a change owns one role and never holds another's: the
proposal owns why, what changes, the deliverable and pre-authorized
actions, and the installed behavior; the delta specs own the behavior
contract; the design owns the approach's bounds and the information
needed only for this change; the tasks own steps with their verification.
Two tests place a fact: a rule that would hold under any approach goes
with the specs or the proposal, one that holds only under the chosen
approach goes in the design; information needed the next time the skill
changes goes in the spec, information needed only for this change goes in
the design. What each artifact contains, and when a design is required,
is the project schema's instruction for it
(`openspec/schemas/skill-change/schema.yaml`).

## Domains

- One domain per public skill, at the skill's catalog path:
  `openspec/specs/<catalog>/<skill-name>/spec.md`. Its requirements
  describe what an agent that loaded the skill observably does; its
  scenarios are the skill's behavioral test cases. A skill that moves
  catalogs moves its domain in the same change.
- The repository itself — environment, harness, tooling, checks,
  workflows, documents — has no spec domain. A change to it is a
  **repository change**: an OpenSpec change whose `.openspec.yaml` sets
  `skip_specs: true`, with a proposal, a design, and tasks and no delta
  spec. Its acceptance is the verification plan in its design.
- A domain exists only once a change touches it. Never backfill specs for
  skills nobody is changing.

## Source of truth

| Fact | Rules | Points to it |
|---|---|---|
| What the repository is for | `README.md` | this file, `openspec/config.yaml` |
| Skill quality and conventions | `.agents/knowledge/skill-quality.md`, `AGENTS.md` | `openspec/config.yaml`; specs never restate them |
| Behavior of a public skill | `openspec/specs/<catalog>/<skill-name>/spec.md` | issues, pull requests, behavioral tests |
| Acceptance of a skill change | the scenarios in `openspec/changes/<slug>/specs/` | the Task form's Specification field, the PR's `Spec:` line |
| Acceptance of a repository change | the verification plan in its `design.md` | the same two links |
| Repository mechanics | `ARCHITECTURE.md` and the knowledge files | specs never restate them |

A file listed under "Points to it" may summarize in one line and must
link; it never restates the fact.

## Lifecycle

Combined shape: one pull request carries the whole lifecycle of its
change, because this repository ships skills feature by feature and no
consumer depends on a stable contract (installed copies are never updated
in place). A skill change that also needs harness work carries a
companion repository change `<slug>-harness` on the same branch. The
implementing agent writes the specification; the maintainer approves.

1. **Proposed** — the change directory holds its approval package: the
   proposal, the delta specs (none for a repository change; the
   `plan-clarification` skill runs the clarify step until no assumption
   is silent), and the design whenever the schema requires one. The
   draft pull request opens once that package is committed, with the
   package as its first content — never before the design, never after
   the task list.
2. **Approved** — the agent stops at the draft. The maintainer discusses
   the package there — the outcome description and the design's bounds,
   never `tasks.md` — and directs record changes in conversation, each
   pushed through the publish gate. The maintainer closes the package
   deliberation as `## Approval gates` describes; the agent reconciles
   it, then writes `tasks.md` and implements. An agent never closes a
   deliberation on a change it wrote.
3. **Implemented** — every task done and ticked, every scenario passed
   (for a skill, the behavioral tests of the `skill-authoring` project
   skill, planned in the design). The agent marks the pull request ready
   under `agent-authority.md ## What agents may do`, which opens the
   second deliberation, on the finished implementation, with the change
   still unarchived (`## Archive executor and the freeze`).
4. **Archived** — the maintainer closes the second deliberation in
   conversation, the agent reconciles it, and the record is frozen by
   the executor in `## Archive executor and the freeze`.
   `checks / archived` reports; the maintainer merges.

Task ticking: tick a task only when its verification ran; a fully ticked
task list is what the archive consumes.

Deviation found during implementation: stop, revise the change
(`openspec-update-change`), have the maintainer discuss and close the revision on the
pull request as in step 2, then continue.

## Approval gates

- **Package closing** — the maintainer adds the `spec/approved` label.
  `spec / labels` then writes one record comment as `github-actions[bot]`
  naming the approved head, the account, and the label event, and it
  withdraws the approval, putting `spec/pending` in place of
  `spec/approved`, when the package changes after the recorded head, when
  a person removes `spec/approved` or adds `spec/pending`, when a run
  fails, or when its deciding step times out; the maintainer approves
  the new package by adding `spec/approved` again. The package is every
  file of each of the pull request's own unarchived changes except
  `tasks.md`, plus the main spec under each delta; its own changes are
  those the base does not hold identically, so a pull request into
  another pull request's branch answers only for what it brings. An
  archive commit is not a package change, and after it `spec/archived`
  replaces `spec/approved` with the record left live; a withdrawal by a
  person after the archive still gives `spec/pending` and withdraws the
  record.
  Only the run the label event starts writes the record; if that run is
  replaced while pending, the next run finds the label without a record
  and withdraws it, and the maintainer adds the label again.
  The label proves a deliberate write-access act bound to one package,
  not the maintainer's identity, so:
  - after asking for approval, the agent pushes nothing to the package
    until the record appears;
  - the maintainer checks that the recorded commit is the one reviewed;
  - the agent reads the approval with `just spec-approval <n>` (it
    recomputes the state and writes nothing) before marking ready;
  - setting or removing the label and editing the record are the
    maintainer's alone (`agent-authority.md ## What agents may not do`).
- **Bootstrap** — the label exists only once `labels / sync` has run on
  `main` with it in `.github/labels.json`. Until then the package closing
  is the maintainer's word in conversation, noted on the `Approval:` line.
- **Implementation closing** — the freeze stays conversational: the
  maintainer closes the second deliberation in conversation.
- **Reconciling** — on each closing the agent lists every unresolved
  review thread, requested adjustment the record does not carry, and
  contradiction, and proceeds only when nothing is open or the maintainer
  confirmed the open items (procedure: the `change-workflow` skill, §3).
- **Phase and approval lines** — the pull request body's `Phase:` reads
  `specification` until the package closing is reconciled and
  `implementation` from then on; its `Approval:` line names the
  deliberation that is open, then each closing with its date, and the
  freeze commit. `pr / policy` requires `Phase: implementation` on a
  ready pull request.

## Archive executor and the freeze

Every change is archived inside its own pull request, after the
maintainer closes the second deliberation and the agent reconciled it, so
`main` never holds an unarchived change. The pull request is ready before
the archive, so through the whole second deliberation it shows
`checks / awaiting-archive` and an expected, unreported
`checks / archived`, which the ruleset requires: the merge waits and
nothing is red (`github-checks.md ## No standing failure`). That is the
expected state, not a defect to chase or to report. Freezing early hands
the maintainer an archived record to deliberate on. No pull request into
`main` merges with an unarchived change, not even one that implemented
nothing; a pull request into another pull request's branch may keep its
change open.

The executor is one command, run by the implementing agent on the branch
(on a fork, by whoever holds the branch):

```bash
just spec-changes archive --base origin/main --head HEAD
```

It refuses while any related change has an open task, archives every
related change (a skill change's delta lands in `openspec/specs/`; a
repository change's record only moves under `openspec/changes/archive/`),
and runs strict validation. Commit the result as
`docs: archive the <slug> change`. The generated `openspec-archive-change`
skill archives one change and only warns on open tasks; never use it
here. No workflow archives: a platform token cannot push to a fork, and
the job would be the only one needing `contents: write`.

The archive commit is the freeze: the version the approval names. A
defect found in the frozen record goes to the pull request's Validation
section or a follow-up change, never into the archive. Nothing revokes
the maintainer's closing, so a commit after the archive commit means the
approved version no longer exists: compare the tip with the archive
commit before pushing or handing over, say so, and ask again.

## Request automation

A pull request's *related changes* are the change directories its diff
touches (an archived directory counts under its change name), resolved by
`scripts/spec_changes.ts`.

- `checks / spec` runs the strict validator and warns on each unarchived
  related change; on a push to `main` any change outside `archive/` fails.
- `checks / archive-verdict` and its carrier hold a pull request into
  `main` with an unarchived related change on the required
  `checks / archived` (`github-checks.md ## No standing failure`).
- `spec / labels` keeps one state label: `spec/pending` while the head
  holds an unarchived change whose approval does not hold, `spec/approved`
  while it holds, `spec/archived` when the pull request archives its
  change, and none otherwise (`## Approval gates`). Only the maintainer
  adds `spec/approved` or `spec/pending` by hand; task progress is
  `just spec-changes status`.

Locally, `just spec-check` reproduces the check and
`just spec-changes <command>` the rest.

## Specifications and tracked work

- The change owns what is built, why, and the acceptance.
- An issue owns who, when, and status. It opens when the requirement
  appears, with the raw requirement, owner, and priority and no acceptance
  criteria; its Task form Specification field links the change once the
  change exists, and its acceptance field holds either executable
  criteria or a link to the change's scenarios, never both. Discussion of
  a specification in an issue thread is deliberation; the record is the
  file on the branch.
- A pull request names each change on its own `Spec:` line, a link to the
  change directory on its branch:
  `Spec: [openspec/changes/<slug>](https://github.com/ryan-minato/skills/tree/<branch>/openspec/changes/<slug>)`.
  The other fields are the pull request template's. Tracker objects
  navigate to the record; they never copy it.
- `Spec: none — <reason>` replaces the change only for a change too small
  to plan: a pin bump, a typo.
- Bug reports carry no spec: the expected behavior is the current spec,
  and the fix's change carries the delta.

## Verification in checks

`just spec-validate` runs the OpenSpec validator in strict mode over every
spec and change; `just check` includes it. The `checks / spec` job runs
`just spec-check` on pull requests and `just spec-changes check --all` on
`main`, then regenerates the OpenSpec skills and fails if the committed
copies differ.

## Update this file when

- `openspec_version` in the `justfile` changes: run `just spec-sync` and
  re-verify the artifact table against `openspec --help`.
- The level, the approval owner, mode, or label, the change request
  shape, or the archive executor changes; a workflow, command, or label
  of the request automation is added, renamed, or removed.
- A domain naming rule or the catalog layout changes.
- The project schema gains, loses, or reshapes an artifact: update the
  artifact table, `skill-authoring`, and the pull request template
  together.
- A second source of truth for any fact here appears: merge it back.
