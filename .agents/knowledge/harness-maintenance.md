# Harness Maintenance

Read this when a file that another file mirrors changes, when a tool pin
is bumped, on the first pull request of each quarter, and whenever a
catalog is added or removed. It holds the two things that keep this
harness true to the repository: the register of copied facts and their
owners, and the periodic entropy review.

Decision on record (2026-09-03, maintainer): GitHub is this repository's
only remote and task platform. The knowledge files are written in GitHub
terms, as every `meta` contract builder deposits them; only the builders'
disposal step does not apply here (see `## Use inside this repository` in
`skills/meta/CONTEXT.md` and `skills/scaffold/CONTEXT.md`).

## Layer calibration

Read before changing the thickness of any layer. Rated 2026-10-19; the
variables: error cost high (every skill is installed by other projects),
maintenance horizon indefinite, isolation a dev container with no secrets
beyond the forwarded `gh` login, autonomy attended at H1, team one
maintainer plus agents.

| Layer | Rating | Variable and reason |
|---|---|---|
| Environment and sandbox | medium | isolation: container, no mounts, no credential beyond `gh`; no isolation tier needed (`agent-authority.md`, Threat model) |
| Knowledge and routing | thick | horizon: entrypoint, eight knowledge files, three project skills, pointers checked by `validate_harness.ts` |
| Hard gates | thick | error cost: pre-commit (secret scans, validators, ruff) and CI (`checks / gate`, `pr / policy`, `scan-secrets`) required |
| Authorization boundary | medium | autonomy attended: allow and deny lists, pre-authorized actions, pending decisions, H1 policy; thick only if a run becomes unattended |
| Specification and completion criteria | thick | error cost and horizon: OpenSpec spec-anchored, strict validation in CI, two deliberations |
| Entropy management | thick | horizon: this register, `validate_harness.ts`, the review below |

## Periodic entropy review

Cadence: quarterly, on the first pull request of the quarter, and after
any catalog change. Last run: 2026-09-11 (the `machine-learning`
catalog): keep — `AGENTS.md`, the dependency grants in
`skill-quality.md`, and the domain rule in `spec-workflow.md` need no
change for a catalog that reserves no prefix and grants nothing; the
settings readback (step 4) is left to the maintainer.

1. Run `just check`; every documented command in `AGENTS.md`,
   `ARCHITECTURE.md`, and the project skills must still run.
2. Read `AGENTS.md` for length (about 100 lines), stale paths, and rules
   stated twice; every knowledge file must still have a pointer whose
   trigger can fire.
3. Compare each knowledge file's "Update this file when" list with what
   actually changed since the last run; update or delete stale content.
4. Compare `.agents/knowledge/github-settings.md` with a fresh readback of
   every row.
5. Check the "not used" triggers in `.agents/knowledge/github-workflow.md`
   and the omitted-object list; enable only what fired.
6. Ask of each constraint whether it has caught anything since the last
   run and whether the work still justifies its thickness; one that
   catches nothing is a thinning candidate. Look for project
   skills whose trigger never fired since the last run.
7. Record findings as keep / update / remove, apply the unambiguous ones,
   and update the "Last run" date above in the same pull request.
