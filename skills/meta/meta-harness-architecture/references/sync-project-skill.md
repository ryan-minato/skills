# Skill-Family Sync Mechanisms

Read when the plan's sync family is skills. Each sync concern becomes one
durable project skill whose description fires on the concern's forward
trigger — auto-triggering is this family's advantage, so spend it on
precise descriptions.

## Description Writing

The description must name the triggering change in the words a session
would actually contain: "Use when a command, check, or convention changes"
fires; "Use when the harness needs syncing" never does. Include the
reverse direction too: "or when asked to update <document>".

## Per Concern

For each document ↔ artifacts pairing:

- **forward section** — the concrete changes that oblige updating the
  document, and which part of the document each change touches;
- **reverse section** — the artifacts to inspect before editing the
  document ("before updating, check that these commands still run, these
  paths exist, these headings still match their pointers"), and the
  instruction to fix or report every mismatch found, not only the one
  that prompted the edit;
- **completion criterion** — what verified looks like (links resolve,
  commands run, the doc says nothing the code contradicts).

## Boundaries

- One skill per concern. A single mega-sync skill has an untriggerable
  description; per-concern skills fire exactly when their subject moves.
- Sync skills are durable: their descriptions must never begin with the
  marker the disposable builders carry.
- If a concern's document is external (an issue tracker document, a wiki
  page), the reverse section carries the extra weight: external content
  does not version with code, so every touch inspects.
