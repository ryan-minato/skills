# Community and Contribution Files

Read when the approved harness includes CONTRIBUTING, SECURITY, SUPPORT,
CODE_OF_CONDUCT, GOVERNANCE, license guidance, or other human-facing project
policy.

Inventory existing files, project visibility, outside-contribution policy, and
the real owner/contact for every proposed document. Verify through current
GitLab docs which files the target version surfaces automatically. Link any
useful unsurfaced file from the README.

- **CONTRIBUTING:** document real setup, local checks, issue/task intake,
  branches, commits, early draft MRs, review, and where to ask questions.
- **SECURITY:** give a private monitored reporting channel, supported scope or
  versions, response expectations, disclosure process, and owner. Never direct
  vulnerabilities to public issues.
- **SUPPORT:** list only channels somebody monitors and distinguish support
  from reproducible defects and feature/task intake.
- **CODE_OF_CONDUCT:** adopt an established current text; record a real
  enforcement contact. Do not invent legal/policy text from scratch.
- **GOVERNANCE:** create only when decision rights, roles, escalation, or
  succession need a public contract. Name actual roles and processes.
- **LICENSE:** the user makes the legal choice. Fetch canonical license text
  from its authoritative source and do not paraphrase it.

Reconcile public statements with the agent harness and templates. A change to
setup/check commands updates CONTRIBUTING in the same MR; a change to reporting
or ownership updates SECURITY/SUPPORT/CODEOWNERS and their entrypoint pointers.

Do not create a file without a real audience, owner, and maintenance trigger.
Public files remain human-first and require human review before publication.
