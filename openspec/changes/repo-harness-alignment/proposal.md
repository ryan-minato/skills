## Why

This repository's harness grew by accretion and now fails the methodology it publishes. An audit on 2026-10-20 (six-layer model, file:line evidence) found 36 rules stated more than once — the freeze rule 18 times in 10 files — so a change to one rule is an edit hunt; four contradictions between files that load together (a project skill archives before the pull request opens, the review skill blocks every ready pull request, two archive executors, a validator message that prints an install command); 17 stale or transitional passages; table rows up to 918 columns; 19 rules enforced by nothing, among them the publish gate, workflow security beyond `pull_request_target`, and the commit-safety scan a `--no-verify` skips; and about 3,300 lines of management scripts with no test, reading YAML with regular expressions. The two reference harnesses this repository's builders deposited (`hoshiori-dev/devcontainer-features`, `hoshiori-dev/devcontainer-templates`, both public) show what holds up over 63 changes and what decays, and the harness specification this library implements names the execution-level layers this harness lacked. This change rebuilds the harness on that evidence: it gates the unenforced rules a check can decide, records the rest as review items with their owners, and drops what the references show decays.

## What Changes

Environment and toolchain
- Development tools are never pinned: the dev container and CI install the latest Deno, just, pre-commit, and ruff, so a security fix arrives without a version bump and a breaking release shows at once. The maintainer's working-tree switch of `.devcontainer/devcontainer.json` to the `deno` and `uv` features (tools unpinned) is folded in, except that the Python feature it removes stays (without tools) until the last Python caller is ported, because the hooks and the unported scripts still run `python3`; the feature lockfile and the skills lockfile stay ignored, as today.
- OpenSpec is the one pinned tool, because the generated `openspec-*` skills must equal the pinned CLI's output byte for byte. The `justfile`'s `openspec_version` is its only pin; OpenSpec runs through Deno as `npm:@fission-ai/openspec@{{openspec_version}}`, with no global install and no Node. OpenTofu follows the other tools: `just install-opentofu` installs the latest release, still verified against that release's checksums. A `tools` check replaces the ruff-only `check_ruff`: no file other than the justfile names an OpenSpec version, except the `generatedBy` stamps of the generated skills, which must equal it; and no `deno.lock` is tracked.
- `.github/actions/setup-tools/action.yml` (new): installs the latest Deno always and, only when a job asks through inputs that default to off, the latest just, Python tools, and OpenTofu. Jobs holding a write permission ask for nothing beyond Deno.
- `.pre-commit-config.yaml`: the ruff hooks call the installed ruff, so the hook and `just lint` run one version; the hooks that pre-commit fetches from their own repositories (whitespace fixers, detect-secrets, gitleaks) must name a revision, which pre-commit cannot float, so Dependabot's `pre-commit` ecosystem keeps them current where it applies and `pre-commit autoupdate` runs at the periodic review otherwise.
- `checks.yml` gains a `devcontainer` job, gated through `checks / gate`: when the dev container, the setup action, `justfile`, or `deno.json` change, it builds the container and runs `just check` inside it.
- Actions stay pinned to commit SHAs and are updated by Dependabot, whose scan now covers the composite actions under `.github/actions/*` too.

Management code in Deno
- Every script under `scripts/` and `.agents/skills/change-workflow/scripts/` is ported from Python to TypeScript run by Deno: `scripts/<name>.ts`, executable, with a `#!/usr/bin/env -S deno run --no-prompt …` shebang granting only the permissions it needs, and a `scripts/<name>_test.ts` beside it. Callers run `./scripts/<name>.ts`. Each Python file is deleted once its port matches its output on the recorded baseline, except for the intentional differences the design lists.
- `deno.json` (new) with an import map of `jsr:@std/*` modules by major-version range, `"lock": false`, `deno.lock` ignored, and the `tools` check failing a tracked one, and `fmt`/`lint` settings whose `include` names only the TypeScript management code — no Markdown, JSON, or YAML is formatted, and nothing under `skills/`, `openspec/`, or `.agents/skills/openspec-*` is ever in scope. YAML is read with `@std/yaml`.
- Unused modes are dropped, not ported (`gen_marketplace --check`, `check_skill --all`, the commit-safety layer printout, which gates nothing); diagnostics go to stderr; `run_log_digest` fails, naming the job, when a log cannot be fetched instead of exiting 0 with an empty tail.
- `just test` (new) runs `deno test`; `just lint` runs `deno lint`, `deno fmt --check`, and `deno check` on the management code and keeps `ruff` on the public skills' Python only; `just check` runs both and no longer runs the validators and ruff a second time through pre-commit.
- Every workflow `run:` line, path filter, recipe, and hook that names a Python script is moved to its port; the `checks / spec` and `labels / sync` path filters also name `scripts/lib/` and `deno.json`, which the ported scripts import.

Hard gates
- A parsed workflow check replaces the regular-expression one and also reads `.github/actions/*/action.yml`: every workflow and job declares `permissions`; every external action is pinned to a commit SHA with a version comment; every `actions/checkout` sets `persist-credentials: false`; every job sets `timeout-minutes`; no `${{ github.event.* }}` or `${{ github.head_ref }}` expression reaches a `run:` line or a `script:` input; the privileged triggers (`pull_request_target`, `issue_comment`, `issues`) appear only in the workflows `github-checks.md` lists, whose jobs never check out, fetch, or run pull request content and use no action but the checkout and the setup action with no tool inputs; no script a privileged job runs imports a remote module, since no lockfile pins one; no workflow uses `workflow_run`; no `pull_request` workflow grants a write permission.
- `.pre-commit-config.yaml` gains `no-commit-to-branch` for `main`, so a local commit on `main` stops at the hook.
- The `checks / gate` aggregator becomes a tested script (`scripts/ci_gate.ts`) that fails on a failed, cancelled, or unexpectedly skipped dependency and names it.
- `pr / policy` runs a commit-range scan from the base's copy: each commit's own added lines for credential patterns; each commit's author email for a noreply address on same-repository pull requests (fork commits are squashed); and no agent-attribution trailer (a `Co-Authored-By` line naming an AI model or a model vendor's noreply address, a "Generated with" tool line). The local `--allow-private-email` override is dropped: no private email lands on `main`.
- `pr / policy` moves to Deno through a guarded transition: it installs the latest Deno with the SHA-pinned external setup action and runs `./scripts/check_pr_policy.ts` when the base checkout has it, else the base's Python script. A follow-up change removes the fallback once `main` holds the port.
- Package approval becomes a label the automation keeps: the maintainer adds `spec/approved` to close the package deliberation; `spec / labels` records the approved head, the account, and the label event in one comment from `github-actions[bot]`, decides from the pull request's current timeline rather than from the triggering event, and withdraws the label when the approval package — every file of each unarchived change except `tasks.md`, plus the main spec under each delta — changes after the recorded head, when a run fails, or when its deciding step times out. `scripts/spec_approval.ts` decides it; `just spec-approval <n>` prints the state without writing; the agent reads it before marking a pull request ready. The label records a deliberate write-access act bound to one package, not the maintainer's identity: agents use the maintainer's `gh` login, so adding or removing the label, and editing or deleting the record comment, are the maintainer's alone and denied to agents; after asking for approval an agent pushes nothing to the package until the record appears, and the maintainer checks that the recorded commit is the one reviewed. The freeze stays a conversational decision.
- `.claude/settings.json`: `deny` gains any command naming `spec/approved`; an `ask` list, each entry with its reason in `agent-authority.md`, covers the outward-write families — `git push`, `gh pr` create/edit/ready/comment/review/close/reopen, `gh issue` create/edit/comment/close, `gh label`, `gh workflow run`, `gh run rerun`/`cancel`, `gh api graphql`, and `gh api` with a field or body flag or a write method; the review-threads read runs through `just review-threads <n>` (a fixed read-only query) and the issue-comments read through `gh pr view --json comments`, replacing the two wildcard `gh api` allow entries. Like the deny list, these entries guard against mistakes; a reordered command gets past a prefix rule, and the container stays the boundary.

Repository settings
- `.agents/knowledge/github-settings.md` is rewritten as the declaration of the intended repository settings, one row per setting with its current and intended value and the read-only command that shows it: among them, Actions restricted to GitHub-owned actions and an allowlist of the third-party actions the workflows use, actions required to be pinned to a full-length commit SHA, the merge methods, the ruleset, and the security features. After this change is fully implemented and archived, the maintainer applies the rows whose value differs; the agent then reads every row back and records the dated result in the pull request description.

Knowledge and routing
- Every rule has one owner file; every other place holds a pointer or nothing (the owner map is in the design). `AGENTS.md` returns to its budget of about 100 lines, its `## Always` holding one line per always-on rule with its owner.
- `.agents/knowledge/management-code.md` (new) owns the rules for the repository's own code: the Deno script shape, permissions, tests, workflow security, and tool pins. `skill-quality.md` keeps the bar for public skills, and a `## Script assets` section there keeps the rules for the Python scripts the skills ship (R1–R6, fail-fast, the Python floor, the lint exceptions); `ruff.toml` changes only its header comment.
- Wide tables are rebuilt so no row passes 200 columns.
- The contradictions are resolved: one archive executor, `just spec-changes archive`, owned by `spec-workflow.md`, which also says the generated `openspec-archive-change` skill is not this repository's executor; `skill-authoring` and `code-review` point to the lifecycle instead of restating it; the validator's self-containment message routes through the installing skill, and a validator check fails on an install command inside a public skill other than `ryan-minato-skills-installing`; `CONTRIBUTING.md` matches the lifecycle and the new toolchain and opens with a banner that the knowledge base governs agents; `github-checks.md` states the Dependabot exemption of `pr / policy`.
- Stale passages are removed or rewritten as dated observations; `pr / policy` stops accepting a bare `Spec:` path, which only one closed pull request used; the guard against a legacy plugin manifest stays, since it is live protection rather than stale text.

Entropy management
- `harness-maintenance.md`: the synchronization register as short rows (file pair, owner, check or trigger), the layer calibration re-rated, and this rebuild recorded as the quarter's periodic review, including a read-only readback of every `github-settings.md` row before ready, which lists the rows the maintainer applies after the archive; the readback after that is recorded in the pull request description, since a commit after the archive would spend the approval, and the next change copies it into `github-settings.md`.
- A budget check in the validator: `AGENTS.md` within its line budget, and no table row over 200 columns in the entrypoint, `ARCHITECTURE.md`, or the knowledge files.

## Installed behavior

Agents in this repository read one owner per rule and an entrypoint that fits its budget; run management scripts as executables whose permissions say what they touch, with tests that run in `just check`; see workflow security and a skipped commit hook fail as checks; read the package approval through `just spec-approval`, which recomputes it, and never set the label themselves; meet a framework prompt on the common forms of outward writes; and run the latest development tools in the container and in CI, with only OpenSpec pinned, in the justfile alone.

## Impact

- Files: `.devcontainer/devcontainer.json`, `.gitignore` (`deno.lock`); `.github/actions/setup-tools/` (new); every workflow under `.github/workflows/` (setup steps, `run:` lines, path filters, checkout options, timeouts); `.github/dependabot.yml`, `labels.json`, `PULL_REQUEST_TEMPLATE.md`, `CONTRIBUTING.md`; `scripts/*` (Python removed, TypeScript added; the `pr / policy` fallback runs `main`'s Python copy until the follow-up), `.agents/skills/change-workflow/scripts/`; `deno.json` (new); `justfile`, `.pre-commit-config.yaml`, `ruff.toml` (comment only); `.claude/settings.json`; `AGENTS.md`, `ARCHITECTURE.md`, every file under `.agents/knowledge/`, `management-code.md` (new); the three project skills; `openspec/config.yaml` and the project schema where they restate a rule.
- Untouched by design: everything under `skills/` — no skill text, reference, asset, or script of a public skill changes, and ruff's selection over them is byte-identical; the generated `openspec-*` skills; archived changes; `README.md`/`README.zh.md`; `marketplace.json`.
- After the archive: the maintainer applies the settings `github-settings.md` declares, and the agent records the readback.
- After merge: `labels / sync` creates `spec/approved`; the first pull request, comment, and issue event prove the privileged workflows on `main`'s copy; a follow-up change removes the `pr / policy` Python fallback.

## Non-goals

- No change to any public skill. Back-porting the shapes proven here (the label approval, the workflow check) into the `meta` builders is a later change of those skills.
- No OpenSpec version bump.
- The required checks keep their names (`checks / gate`, `pr / policy`, `scan-secrets`); settings change only as `github-settings.md` declares, applied by the maintainer after the archive.
- No check on the approval label inside `pr / policy`: as in the reference harness, the label is read by recomputing it, never as a merge check; a check would race the withdrawal it depends on.
- No separate agent account or token to tell an agent's label from the maintainer's.
- No checks for the remaining rules the audit found enforced by nothing, because a check would need judgment or cost more than it catches: draft timing and `tasks.md` after the closing, branch naming, squashing drafts before a push, commit scope naming a skill, README pair content, the reasons allowed for `Spec: none`, an agent closing its own deliberation, never weakening a check. They stay review items with their owners, re-read at the next periodic review.
- No approval artifact bound to a digest with an expiry, no API-posted check runs from a privileged job, no unpinned action references, no duplicated generated skills, no harness rules written as specification domains: the reference harnesses show their cost outweighs their use for a one-maintainer repository.
- No CODEOWNERS or required review count: the repository has one maintainer.
