## Purpose
Governs what an agent that loaded `devcontainer-authoring` observably delivers when it scaffolds or maintains a Dev Container Feature or Template collection: the management code of the scaffolds (CI workflows, composite actions, test and smoke scripts, `justfile` recipes), how that code fails, and the feature tests the agent writes.

## ADDED Requirements

### Requirement: Behavior: Feature collection management code hides no unexpected failure
The workflows, composite actions, test scripts, and recipes the agent delivers for a Feature collection SHALL hide no unexpected failure behind a fallback, the matrices that finish every leg before failing being marked where they are written, and a missing `test/<id>/compatibility.txt` keeping its documented default of `mcr.microsoft.com/devcontainers/base:ubuntu`.

#### Scenario: Feature collection scaffolded
- **WHEN** the user, in an empty git repository, asks "Set up a GitHub repository for our team's Dev Container Features, starting with a feature that installs ripgrep"
- **THEN** the delivered workflows, composite actions, and `justfile` match the scaffold's assets apart from the feature id and owner placeholders, the feature's `test/<id>/` holds `test.sh` and `duplicate.sh`, no delivered step reads an unexpected failure as success, and every matrix that finishes all its legs before failing carries a comment saying so

#### Scenario: Malformed manifest checked locally
- **WHEN** `just validate` runs in a Feature collection holding two feature manifests, the first of which does not parse
- **THEN** it names the malformed manifest, reports the second as checked, and exits non-zero

#### Scenario: Matrix input is not an array
- **WHEN** the build-test-matrix step runs with a `features` input of `{bad` or of `{}`
- **THEN** it exits non-zero with a message naming the input and the value received, and writes no `matrix` output

#### Scenario: Feature list unreadable
- **WHEN** the full-sweep workflow's feature-list step runs and `jq` fails
- **THEN** the step exits non-zero and writes no `features` output

#### Scenario: Compatibility file declares no image
- **WHEN** a feature's `test/<id>/compatibility.txt` holds only comments and blank lines, and the build-test-matrix step or `just test-compat <id>` runs
- **THEN** each exits non-zero with a message naming the file, and neither reports the feature as tested

#### Scenario: Compatibility file absent
- **WHEN** a feature has no `test/<id>/compatibility.txt`, and the build-test-matrix step or `just test-compat <id>` runs
- **THEN** the feature is tested on `mcr.microsoft.com/devcontainers/base:ubuntu` alone

#### Scenario: Every declared image tested locally
- **WHEN** `just test-compat <id>` runs for a `compatibility.txt` declaring four images, with a `devcontainer` command that reads its standard input to the end
- **THEN** `devcontainer features test` is invoked once for each of the four images

#### Scenario: Per-feature test mode without a feature
- **WHEN** the shared run-feature-test step runs the `autogenerated`, `duplicate`, or `scenarios` mode with an empty `feature` input
- **THEN** it exits 2 with a message naming the mode, and `devcontainer` is not invoked

#### Scenario: Asserted command fails after printing
- **WHEN** each check in the scaffold's example feature tests that asserts `hello-tool`'s output runs on its own, under its file's `set -e` header with the Dev Container CLI's test library, against a `hello-tool` that prints the expected greeting and exits 1
- **THEN** it prints `❌ <label> check failed` with its own label, and the script running it exits non-zero

#### Scenario: Changed-feature output missing
- **WHEN** the change-detection job of the fast test workflow succeeds with an empty `features` output
- **THEN** the test job's condition does not read the empty output as "nothing changed", so the job is not skipped and reading its matrix fails the run

### Requirement: Behavior: Feature tests the CLI would skip are required or skipped visibly
The shared test action and the `test-duplicate` recipe the agent delivers SHALL fail, naming the file, when the duplicate mode runs for a feature without `test/<id>/duplicate.sh`, and the shared test action SHALL turn the Dev Container CLI's silent skip of a missing `test/<id>/scenarios.json` or `test/_global/scenarios.json` into a skip announced with a notice that names the file, with a comment where the skip is decided.

#### Scenario: Idempotency test script absent
- **WHEN** the shared run-feature-test step runs the `duplicate` mode, or `just test-duplicate <id>` runs, for a feature that has no `test/<id>/duplicate.sh`
- **THEN** each exits non-zero with a message naming `test/<id>/duplicate.sh`, and `devcontainer` is not invoked

#### Scenario: Feature without scenarios
- **WHEN** the shared run-feature-test step runs the `scenarios` mode for a feature that has no `test/<id>/scenarios.json`
- **THEN** it writes a `::notice::` naming `test/<id>/scenarios.json`, does not invoke `devcontainer`, and exits 0; the branch that decides the skip carries a comment saying the file is optional

#### Scenario: Collection without global scenarios
- **WHEN** the shared run-feature-test step runs the `global` mode in a collection that has no `test/_global/scenarios.json`
- **THEN** it writes a `::notice::` naming `test/_global/scenarios.json`, does not invoke `devcontainer`, and exits 0; the branch that decides the skip carries a comment saying the file is optional

### Requirement: Behavior: Template collection management code hides no unexpected failure
The workflows, smoke-test action, smoke script, test script, and recipes the agent delivers for a Template collection SHALL hide no unexpected failure behind a fallback, the smoke script's container cleanup being marked as best effort that reports what it could not remove and never changes the test's exit status.

#### Scenario: Template collection scaffolded
- **WHEN** the user, in an empty git repository, asks "Create a Dev Container Template repository with a Python template whose boolean option installJupyter defaults to false"
- **THEN** the delivered workflows, smoke-test action, smoke script, and `justfile` match the scaffold's assets apart from the template id and owner placeholders, the template has a `test/<id>/test.sh`, and no delivered step reads an unexpected failure as success

#### Scenario: Changed-template output missing
- **WHEN** the change-detection job of the template test workflow succeeds with an empty `templates` output
- **THEN** the smoke job's condition does not read the empty output as "nothing changed", so the job is not skipped and reading its matrix fails the run

#### Scenario: Malformed template manifest checked locally
- **WHEN** `just validate` runs in a Template collection holding two template manifests, the first of which does not parse
- **THEN** it names the malformed manifest, reports the second as checked, and exits non-zero

#### Scenario: Unreadable template manifest
- **WHEN** the smoke script runs for a template whose `devcontainer-template.json` does not parse
- **THEN** it exits non-zero with a message naming the manifest, and `devcontainer up` is not invoked

#### Scenario: Test script fails
- **WHEN** the smoke script runs for a template whose `test/<id>/test.sh` exits 1 inside the container
- **THEN** the smoke script exits non-zero

#### Scenario: Container removal fails after a passing test
- **WHEN** the template's test passes and removing the labeled containers then fails
- **THEN** a warning names the containers left behind, and the smoke script exits 0

#### Scenario: Test script written for bash
- **WHEN** the template's `test/<id>/test.sh` starts with `#!/bin/bash` and signals its failure as `if [[ ! -e /nonexistent ]]; then exit 1; fi`, a test that exits 0 when `sh` runs it because `[[` is not a command there
- **THEN** the script runs under bash and the smoke script exits non-zero

#### Scenario: Smoke script without its exec bit
- **WHEN** `.github/actions/smoke-test/smoke.sh` has mode 644 and `just smoke <id>` or the smoke-test action runs
- **THEN** the smoke script runs

#### Scenario: Example test command fails
- **WHEN** the scaffold's example `test/hello-template/test.sh` runs under `sh` with an `id` command that exits 1
- **THEN** the test script exits non-zero

### Requirement: Behavior: The template smoke test substitutes every declared default
The smoke script the agent delivers SHALL substitute each option's declared `default` into the template copy, `false` and the empty string included, and SHALL refuse, naming the template and the option, an option that declares no `default`.

#### Scenario: Boolean default false
- **WHEN** the smoke script runs for a template whose option `installJupyter` declares `"default": false` and whose payload contains `${templateOption:installJupyter}`
- **THEN** the copy the container starts from contains `false` in its place, and `devcontainer up` is invoked

#### Scenario: Empty string default
- **WHEN** the smoke script runs for a template whose option `extraPackages` declares `"default": ""`
- **THEN** the placeholder is replaced with nothing, and `devcontainer up` is invoked

#### Scenario: Option without a default
- **WHEN** the smoke script runs for a template whose option `pythonVersion` declares no `default`
- **THEN** it exits 1 with a message naming the template and `pythonVersion`, and `devcontainer up` is not invoked

### Requirement: Behavior: The template smoke test requires the template's test script
The smoke script the agent delivers SHALL fail, naming `test/<id>/test.sh`, when the template has no test script, before any container starts.

#### Scenario: Template without a test script
- **WHEN** the smoke script runs for a template that has no `test/<id>/test.sh`
- **THEN** it exits non-zero with a message naming `test/<id>/test.sh`, and `devcontainer up` is not invoked

### Requirement: Behavior: The release documentation step opens a pull request only on a real change
The documentation step of both scaffolds' release workflows SHALL open a pull request when a regenerated README changed, report no change and exit 0 when none changed, and fail when committing the change fails.

#### Scenario: Nothing regenerated
- **WHEN** the documentation step runs and no `src/*/README.md` changed
- **THEN** it reports that there are no documentation changes, exits 0, and neither pushes nor calls `gh`

#### Scenario: README regenerated
- **WHEN** the documentation step runs and a `src/*/README.md` changed
- **THEN** it commits, pushes the branch once, and runs `gh pr create` once

#### Scenario: Commit fails
- **WHEN** the documentation step runs with a changed README and `git commit` exits 1
- **THEN** the step exits non-zero, and neither pushes nor calls `gh`

### Requirement: Behavior: Feature tests the agent writes fail on the failure they test
When the agent writes or advises tests for a Feature, it SHALL prove repeat installation with the CLI's duplicate mode and a `test/<id>/duplicate.sh`, never with a check that swallows an installer's exit status, and SHALL write each check so that the asserted command's own exit status decides it before its output is matched.

#### Scenario: Idempotency and version tests requested
- **WHEN** the user, in a Feature collection scaffolded by the skill whose feature `mytool` has only `test.sh`, asks "Add tests that mytool can be installed twice and that `mytool --version` reports 1.8.2"
- **THEN** the output adds `test/mytool/duplicate.sh`, run through the duplicate mode (`just test-duplicate mytool`); no check follows an installer with `|| true`; and the version check, run on its own, fails when `mytool --version` exits non-zero even if it printed `1.8.2`
