## Why

The harness methodology this library ships (`core/meta-harness`, mirrored into `meta-harness-architecture`, and run by `meta-harness-building`) calibrates a harness on nine capability-and-constraint layers and says nothing about the threat model that decides isolation, the authorization boundary that decides what an agent may do without asking, the runtime conventions an unattended agent needs (non-interactive execution, commit checkpoints, worktree exploration, handoff hygiene), or deterministic checks on the harness itself. The newer `harness-study` skill already grades six layers by five variables, so the library now studies harnesses with one model and builds them with another. A written specification for agent harnesses (six layers, five variables, soft-boundary loading modes, hard-boundary placement, the lethal-trifecta threat model, reversibility-keyed authorization, commit checkpoints, two-tier harness self-checks) and two public GitHub repositories whose harness the `meta` builders deposited (`hoshiori-dev/devcontainer-features`, `hoshiori-dev/devcontainer-templates`, both public at the time of writing) show the gaps concretely: the deposited entrypoints route well, every pointer and command resolves, the checks are live, and the authority policy enumerates the management actions an agent may and may not take; but nothing the builders wrote decides isolation from a threat model, sets a framework permission list beside the prose policy, tells an agent blocked mid-task to continue and queue the decision, sets checkpoint or squash rules, disables pagers for unattended `gh` and `git` calls, or records where session logs go, and the plan template cannot express per-layer deviation from a preset.

## What Changes

- `core/meta-harness`: the `## Harness Methodology` section (validator-mirrored into `meta-harness-architecture`) replaces the nine-layer capability/constraint calibration with six layers rated by five variables, and adds the principles the methodology lacked: soft boundaries split by loading behavior with process-critical skills routed explicitly and subdirectory carriers limited to local supplements; hard boundaries placed where they are enforced (CI and hooks for defects, sandbox and token scope for secrets, framework configuration as fool-proofing) with native quiet output and error-as-routing; isolation decided by the threat model (assets, open-write input, no human in the loop); an authorization boundary keyed by reversibility with pre-authorized irreversible actions, batched pending decisions, and allow/deny lists without unexplained ask entries; non-interactive runtime with commit checkpoints squashed per task and a per-commit secret scan; drift reports that land in one of three places; and two-tier self-checks for the harness. The domain's `## Purpose` line is corrected by hand in this change, since the domain now governs the whole methodology, not management code alone.
- `meta/meta-harness-architecture`: `references/layers.md` is rewritten around the six layers with light and thick shapes, the two presets, per-layer deviation, hardening, and thinning; four references are added — the security boundary (threat model, sandbox audit checklist, control-plane mutability, readable rejection for unreadable rules), the authorization boundary (capability versus permission, reversibility, pending decisions, permission-list writing, refusal as a decision, policy self-protection), runtime conventions (non-interactive execution, scoped fast checks, checkpoint commits, worktree exploration, handoff hygiene), and harness self-checks (two tiers, management-code rules, failure routing); `references/entrypoint.md` gains the two-part structure, the four-question split test, explicit routing of process-critical skills, and the subdirectory-carrier rule; `references/multi-agent.md` gains shared-resource namespacing, one remote branch per agent, a single coordinator for platform writes, and merge ownership; `references/maintenance.md` gains the three landing places for a drift report, hook-injected reminders as the most reliable sync trigger, session logs as observation, and optional canary tasks; `references/management-code.md` gains output denoising; `references/audit.md` gains the thinning signal and the hardening pass; the entrypoint skeleton puts always-applicable constraints first and adds the authorization and runtime sections; a pending-decisions asset supplies the batched-decision shape; `SKILL.md`'s design axes and load-by-artifact table route to all of it, and the description names the new layers.
- `meta/meta-harness-building`: step 2 settles the five variables and the threat-model and authorization facts after inspection; step 3 and the plan template rate six layers from a preset with per-layer deviation instead of nine capability/constraint rows; `scripts/discover.py` is untouched.

## Installed behavior

An agent that loads `meta-harness` rates six layers separately by five variables and refuses a single project-wide level; places soft boundaries by loading behavior and routes process-critical skills explicitly; keeps security in the sandbox and token scope and treats framework permission lists as fool-proofing; decides isolation from the three threat-model conditions; designs authorization around reversibility, pre-authorizes irreversible actions in the plan, and batches blocked decisions in a fixed shape instead of stopping; sets non-interactive runtime and commit-checkpoint rules; and makes every drift finding land in the change, the pending list, or a tracked item, with reference-integrity and structural checks on the harness itself in long-lived projects. The architecture builder deposits those decisions as project files and loads a reference per layer; the entry builder asks for the five variables and the threat-model facts and presents a six-row plan. This is a `feat`: the methodology gains capabilities (threat model, authorization, runtime, self-checks) and the layer model is replaced by one the library's study skill already uses.
