## Description

`meta-harness-architecture`: the description keeps its lead-in (the practice manual for agent harness layers) and its near-misses (not the build workflow) and adds the new layers to the list it enumerates — the sandbox and threat model, the authorization boundary, runtime conventions (non-interactive execution, checkpoint commits), harness self-checks — and the question phrasings that must load it ("how strictly do we need to sandbox", "which commands may agents run without asking", "how should agents checkpoint"). It must not load for an application test or CI fix, or for studying another repository's harness. Budget: under 1000 characters; the current text is 877, so the additions replace rather than extend where the old list repeats itself.

`core/meta-harness` and `meta-harness-building`: descriptions unchanged. The building domain's Trigger requirement describes the description as it stands.

## Decisions

- **Adopt the six layers from `harness-study` rather than keep nine** (serves every calibration requirement): one vocabulary across study, methodology, and build; the nine rows fold in without loss — information tools into knowledge and routing, workflow tools into authorization boundary, capability tools into environment, target and implementation constraints into specification and knowledge, quality constraints and repository safety into hard gates, workflow constraints into authorization and specification. `layers.md` keeps each folded topic as a paragraph under its new layer so no practice disappears. Rejected: a mapping table beside the nine rows — two models to keep in sync.
- **Five variables, not six** (serves calibration): the methodology's "project lifecycle" is the same fact as maintenance horizon; dropping it removes a duplicate without losing a signal. Rejected: keeping both names.
- **The threat model lives in the environment layer's reference, not a new layer** (serves the security requirement): isolation is an environment decision; the six-layer model stays intact.
- **Execution authorization is a reference in the architecture manual, not a change to `meta-agent-authority`** (serves the authorization requirement): the authority builder governs management gates (review admission, integration) with a contract flow of its own; the execution policy is a harness artifact the architecture builder deposits beside it. Merging them is a later decision recorded in the proposal's non-goals. Rejected: extending the authority asset now — it would reopen a contract builder for a layer that is not a contract.
- **Four new references instead of one "operations" reference** (serves progressive loading): each has a distinct load trigger (environment rated; authorization rated; runtime deposited; entropy rated medium or thick); one file would load three unneeded topics every time.
- **The pending-decisions shape is an asset, not a reference** (serves authorization): it is copied into the target's policy and reworked, which is what assets are for.
- **Checkpoint rules are deposited as rules plus one non-interactive recipe** (serves runtime): agents cannot run interactive rebase, so the rule names the reset-and-recommit sequence and lets the project choose where it lives (recipe, alias, or framework feature).
- **Harness self-checks are described, not shipped** (serves self-checks): each project's check is its own management code in the project's language; a shipped script would be the bound-script defect the methodology forbids.
- **`meta-harness-building` gets a new domain limited to what changes** (serves the building requirements): Trigger plus the requirement round and the six-row plan. Its discovery script and the handoffs are not backfilled.
- **The core `## Purpose` line is corrected by hand** (serves the proposal's naming of the edit): the domain was created for management code alone and now governs the whole methodology.

## Risks / Trade-offs

- [The methodology section grows and is mirrored into the architecture SKILL.md, pushing that body toward its budget] → the new subsections state principles in a few sentences each and route detail to references; the architecture SKILL.md stays well under the 500-line budget (about 335 lines); `just check-skill` reports the body length.
- [Six layers lose a practice that only a nine-row model named] → `layers.md` carries each folded topic under its new layer; the verification plan's calibration case checks that target constraints, capability tools, and repository safety are still addressed.
- [The authorization reference contradicts the deposited management-authority policy] → it defines execution permissions only, names review admission and integration as the authority policy's and never restates them, and the no-self-escalation rule is referenced, not duplicated.
- [Framework-specific carriers (path rules, hooks) are presented as portable] → `entrypoint.md` states they are framework-dependent and that must-hold rules never live there alone.
- [Checkpoint rules conflict with a project's deny list on `git reset`] → `runtime.md` says the rollback precondition is enforced by a recipe and the deny list keeps blocking the raw command.
- [The description change makes `meta-harness-architecture` load for application CI fixes] → the near-miss stays in the description and is in the verification plan.
- [The reference repositories are read as instructions] → they are evidence for the proposal only; nothing is copied, and no requirement names them.
